3. Odkud pochází stavy EV0–EV13

EV není vlastní stavový automat AG Datovka 2. Je to zdrojový kód události v doručence ISDS, který veřejná nápověda popisuje jako informaci o podání, dodání, doručení nebo nedoručení datové zprávy. Implementovaný syntetický profil zachovává zdrojový kód a odmítá kódy mimo svou explicitní mapu; řádek ve fixture proto není důkazem oficiálního významu kódu.

Výsledek implementace: profil explicitně přijímá EV0, EV2, EV3, EV5, EV6, EV8 a EV11; EV1/EV4 (legacy) a EV7/EV9/EV10/EV12/EV13 jsou v tomto profilu odmítnuty jako nepodporované nebo neznámé. Nic se tiše neflattenuje do jiného stavu. Úplná veřejná mapa EV0–EV13 proto zůstává otevřeným compatibility rozdílem, nikoli splněným tvrzením.
Pravidlo implementace: zachováme eventCode, zdrojový profil, typ datové zprávy, aktéra, čas i raw doručenku. Normalizovaný stav bude pouze projekce. Pokud připnuté WSDL/XSD nebo testovací prostředí odhalí další kód či odlišný kontext, nesmí se přepsat do existujícího významu bez nové verze mapy a conformance fixture.

Primární zdroj klasifikace: Doručenky ISDS; historický status EV1/EV4 potvrzuje také nápověda k doručenkám. Veřejná nápověda není náhradou za WSDL/XSD technické přílohy, proto z ní neodvozujeme význam kódů, které výslovně nepopisuje.

5. Kritické konkrétní nálezy baseline

A — Chybí veřejná wire vrstva

Oficiální popis uvádí mimo jiné CreateMessage, MessageDownload, GetDeliveryInfo, seznamy zpráv, GetOwnerInfoFromLogin, ChangeISDSPassword a VoDZ metody. Runtime nic z toho neposkytuje jako SOAP/WSDL endpoint.

B — Špatná semantika lifecycle

Aktuální veřejný popis rozlišuje doručení fikcí, dodání, přihlášení oprávněné/pověřené osoby a přihlášení aplikace. Jedna globální mapa v adapteru tuto informaci ztrácí a některé kódy překládá chybně.

C — Autentizace je jiná vrstva

HS256 bearer token a testovací dev: token chrání moderní management API. To není kompatibilní náhrada za veřejné autentizační mechanismy ISDS aplikací třetích stran ani za mTLS.

D — Kontraktový drift

Fixture deklaruje Correlation-Id jako povinné pro mutace. Runtime jej při chybě doplní z request ID; ověřený POST bez hlavičky vrací 201. OpenAPI navíc definuje IdempotencyKey, ale operace jej systematicky neodkazují.

Časy a náhodné identifikátory v lokálním výstupu nejsou součástí důkazní hodnoty. Důležité je, že testy procházejí a samostatná probe reprodukuje rozpor mezi deklarací a runtime validací.

6. Schválený rozsah implementace

Tato sekce zachovává plán, který byl před implementací předložen ke schválení. Skutečné výsledky a odchylky jsou uvedeny v oddílech 7–9.

Hranice rozsahu: stávající syntetické management API a REST kontrakt zůstávají beze změny a nebudou dále rozšiřovány. Implementace se soustředí na veřejnou SOAP/WSDL kompatibilitu, chování ISDS, doručenky, autentizaci a trust boundary. REST bude pouze interní podpůrná vrstva pro existující UI a testovací orchestrace.

  1. Připnout veřejný kontrakt: uložit syntetickou kopii relevantních WSDL/XSD a technických příloh s verzí, SHA-256 a source profile; oddělit dm_operations, dm_info, db_access, ChangePassword, search a VoDZ.
  2. Přidat kompatibilní gateway: SOAP 1.1 endpoint na explicitním syntetickém hostu, stejné namespaces, operation names, SOAPAction, pořadí XML elementů a faults jako připnutá specifikace. Gateway bude mapovat na stávající domain/pipeline a zůstane bez síťového volání na reálný ISDS.
  3. Opravit lifecycle model: zachovat původní EV kód, typ zprávy, zdrojový profil, raw datum, aktéra a kontext; mapovat EV0–EV13 podle připnutého veřejného významu, oddělit EV11/EV12/EV13, zachovat EV1/EV4 jako legacy a neinterpretovat EV7/EV9/EV10 bez zdroje.
  4. Implementovat autentizaci veřejného rozhraní: pro syntetické prostředí pokrýt přístupové údaje i certifikátovou aplikaci podle veřejné dokumentace; u certifikátu skutečně provést TLS/mTLS handshake, registraci profilu a mapování certifikát → schránka/aplikace. Management OIDC zůstane nezměněn a nebude vydáván za ISDS autentizaci.
  5. Rozšířit trust boundary: gateway/proxy bude vynucovat TLS/mTLS a předávat pouze ověřený identity binding; privátní klíč zůstane mimo API v secret-store handle. Přidat rotation, expired/revoked/wrong-host/wrong-issuer handshakes a explicitní fault/status chování.
  6. Vyřešit payload a VoDZ workflow: nahradit 16 MiB request gate streamovaným/chunked ingestem, parametrizovat běžný limit 20 MiB a VoDZ 100 MB/50 příloh podle připnutého profilu, implementovat veřejné VoDZ operace a ověřit skutečné boundary rejection.
  7. Prokázat klientské workflow: rozšířit SOAP/XML/ZFO fixture, spustit fork proti lokálnímu AG syntetickému endpointu a prověřit login, send, receive, delivery receipt, search, download a export. Veřejný ISDS test použít jen po samostatném schválení; výsledek klasifikovat jako kompatibilní, záměrná odchylka nebo blokující rozdíl.

8. Skutečně provedeno po schválení

  • Contract lock: soap-manifest.json pinne syntetický source profile, retrieval date, endpointy a SHA-256 WSDL/XSD; operace a sekvence jsou v operation matrix.
  • SOAP/WSDL boundary: ag_datovka/soap_gateway.py obsluhuje /isds/ws, kontroluje SOAPAction, namespace, pořadí elementů, base64 přílohy, correlation/request IDs a stabilní SOAP 1.1 faults. Standardní operation surface má 8 operací.
  • Trust/auth boundary: certifikátové facts, hostname/SAN, issuer, key usage, revokace, binding schránky/aplikace a jednorázový nonce se ověřují před adapter normalizací. Management bearer identity není náhradou ISDS identity.
  • Payload and resilience: je vynuceno 0–50 příloh a 100 MiB dekódovaných bytes, včetně deterministického faultu pro 51. QA fixtures pokrývají retry, idempotency, outbox, worker recovery a budoucí výkonové scénáře.
  • Datovka fork: offline harness s pinem 67f1f23056e6f96e4a93632c11418a8ce8ca0b2f prošel login, list, send, receive, download, receipt, search a export proti ag-synthetic profilu.
  • Release verification: integrovaný lokální tip je 89976cf1a7cd9be5eb25b4a0b97346f1aa026c85; v ověřeném release zůstává lokální main shodný s GitHub mirror main. Finální kontrola python3 -m unittest discover -s tests -q skončila 95/95 a git diff --check je čistý.

Podrobné reproducible evidence: AGDA-60, AGDA-62, AGDA-63, AGDA-67 a AGDA-68.

9. Zbývající omezení a další brány

  • Oficiální upstream WSDL/XSD equivalence, živé SOAP faults/provider delivery a produkční interoperability nebyly ověřeny.
  • Skutečný TLS/mTLS handshake, PKI, XML podpisy, durable atomic nonce store a OIDC provider zůstávají integračními hranicemi pro samostatně schválené komponenty.
  • EV1/EV4/EV7/EV9/EV10/EV12/EV13 vyžadují další versioned mapping decision; jejich tiché přijetí by bylo kompatibilitní chybou.
  • Výkonový cíl 1 000 zpráv/minutu je připraven ve scénářích a metrikách, ale měření je výslovně odloženo.

10. Historické rozhodnutí člověka

Před implementací byl schválen zúžený syntetický rozsah: připnuté fixture, SOAP/WSDL gateway, trust/auth boundary, lifecycle/receipt evidence, VoDZ hranice a Datovka fork workflow. Schválení neudělilo přístup k reálnému ISDS ani nepovolilo produkční údaje. Tato prezentace nyní doplňuje skutečné provedení a výše uvádí jeho odchylky a limity.
