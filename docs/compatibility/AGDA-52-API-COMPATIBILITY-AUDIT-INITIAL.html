4. Kritické konkrétní nálezy

A — Chybí veřejná wire vrstva

Oficiální popis uvádí mimo jiné CreateMessage, MessageDownload, GetDeliveryInfo, seznamy zpráv, GetOwnerInfoFromLogin, ChangeISDSPassword a VoDZ metody. Runtime nic z toho neposkytuje jako SOAP/WSDL endpoint.

B — Špatná semantika lifecycle

Aktuální veřejný popis rozlišuje doručení fikcí, dodání, přihlášení oprávněné/pověřené osoby a přihlášení aplikace. Jedna globální mapa v adapteru tuto informaci ztrácí a některé kódy překládá chybně.

C — Autentizace je jiná vrstva

HS256 bearer token a testovací dev: token chrání moderní management API. To není kompatibilní náhrada za veřejné autentizační mechanismy ISDS aplikací třetích stran ani za mTLS.

D — Kontraktový drift

Fixture deklaruje Correlation-Id jako povinné pro mutace. Runtime jej při chybě doplní z request ID; ověřený POST bez hlavičky vrací 201. OpenAPI navíc definuje IdempotencyKey, ale operace jej systematicky neodkazují.

Časy a náhodné identifikátory v lokálním výstupu nejsou součástí důkazní hodnoty. Důležité je, že testy procházejí a samostatná probe reprodukuje rozpor mezi deklarací a runtime validací.

5. Navržená úprava po schválení

  1. Připnout veřejný kontrakt: uložit syntetickou kopii relevantních WSDL/XSD a technických příloh s verzí, SHA-256 a source profile; oddělit dm_operations, dm_info, db_access, ChangePassword, search a VoDZ.
  2. Přidat kompatibilní gateway: SOAP 1.1 endpoint na explicitním syntetickém hostu, stejné namespaces/operation names/faulty jako připnutá specifikace. Gateway bude mapovat na stávající domain/pipeline a zůstane bez síťového volání na reálný ISDS.
  3. Opravit lifecycle model: zachovat původní EV kód, typ zprávy, zdrojový profil, raw datum a kontext; mapovat EV2/EV3/EV5/EV6/EV8/EV11 podle zdroje a doplnit EV12/EV13 i historické EV1/EV4 jako explicitně deprecated/legacy.
  4. Oddělit auth profily: management OIDC zůstane moderní kontrakt; kompatibilní adapter dostane syntetické profily pro přístupové údaje, klientský certifikát/mTLS a další podporované cesty. Každý profil bude mít capabilities, trust anchor, identity binding, revokaci a negativní fixture. Identita občana se nebude tvrdit jako podporovaná přes third-party web services bez důkazu.
  5. Rozšířit trust boundary: gateway/proxy bude skutečně vynucovat TLS/mTLS a předávat pouze ověřený identity binding; privátní klíč zůstane mimo API v secret-store handle. Přidat rotation, expired/revoked/wrong-host a wrong-issuer handshakes.
  6. Vyřešit velikosti a přílohy: nahradit 16 MiB request gate streamovaným/chunked ingestem, parametrizovat běžný limit 20 MiB a VoDZ 100 MB/50 příloh podle profilu, přidat resumable upload a ověřit skutečné boundary rejection.
  7. Urovnat vlastní API: buď vynutit Correlation-Id, nebo odstranit jeho povinnost z fixture; doplnit OpenAPI o všechny skutečné management routes a header references. Přidat contract test, že dokumentace a runtime jsou shodné.
  8. Prokázat klientské workflow: rozšířit offline fixture, spustit fork proti lokálnímu AG syntetickému endpointu a porovnat stejný workflow s oficiálním veřejným testem pouze po samostatném schválení a s účtem vytvořeným pro test. Výsledek musí být klasifikován jako kompatibilní, záměrná moderní odchylka nebo blokující rozdíl.

7. Požadované rozhodnutí člověka

Schvalte prosím tento rozsah implementace: připnuté WSDL/XSD fixture, syntetický SOAP/WSDL gateway, oprava lifecycle semantiky EV kódů, oddělené auth/trust profily, streamované VoDZ hranice a synchronizace OpenAPI/runtime kontraktu. Schválení neuděluje přístup k reálnému ISDS a neumožňuje použití produkčních údajů.

Po schválení: implementace proběhne v navazujícím kroku, přibudou testy a důkazy, a tato prezentace dostane oddíl „skutečně provedeno“ s výsledkem každé akceptační brány. Do té doby je tento dokument pouze auditní baseline a plán.
